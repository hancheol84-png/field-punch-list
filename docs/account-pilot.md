# 계정별 현장 시험 구성

확정 요청: 시험 사용자 5명에게 개별 아이디·비밀번호를 발급한다. 로그인한 사람의 기록만 조회·입력·수정·삭제·엑셀 출력한다. 같은 계정의 휴대폰 기록을 PC에서 열 수 있어야 한다. 각 사용자가 현장·동·호수·위치를 설정한다. 입력 후 7일 보관을 유지한다.

## 구성

- 공개 앱 화면과 코드: 현재 field-punch-list의 GitHub Pages.
- 인증과 비공개 기록: 무료 Supabase 프로젝트 하나. 무료 요금제만 사용하며 유료 부가 기능·유료 음성 API를 사용하지 않는다.
- 서버는 인증 토큰의 사용자 번호를 사용한다. 요청 본문에 다른 사용자 번호를 넣어도 접근 대상을 바꿀 수 없다.
- 인증된 계정 중 관리자가 등록한 시험 사용자만 사용한다. 공개 회원가입은 끈다. 아이디의 내부 이메일 별칭은 인증용 식별자이며 실제 연락처를 요구하지 않는다.
- 브라우저에는 공개용 프로젝트 주소·publishable/anon 키만 둔다. 관리자 secret/service-role 키와 시험 비밀번호를 저장소에 넣지 않는다. 비밀번호 검증·보관은 인증 서비스가 담당한다.
- 외부 CDN 없이 로컬 인증 모듈을 사용한다. 데이터 요청만 비공개 서버 API로 보낸다.

## 계정별 데이터

서버에는 현장 설정, 사용자 확인 보정 규칙, 작성 항목을 계정별로 보관한다. 입력 중 초안과 현재 입력할 동·호수는 각 기기에 보관해 PC 조회가 휴대폰의 입력 위치를 바꾸지 않게 한다. PC에서도 같은 계정으로 로그인한 뒤 최신 기록을 가져와 전체 엑셀을 받는다.

계정별 저장 버전을 검사한다. 다른 기기에서 먼저 수정한 경우 오래된 화면으로 덮어쓰지 않고 동기화를 멈춰 안내한다. 서버 실패·오프라인에서는 현재 기기의 미전송 입력을 남기고 ‘서버 저장 완료’라고 표시하지 않는다. 로그아웃 전에 미전송 항목을 처리하게 한다. 계정을 바꾸면 이전 계정의 화면과 캐시를 분리한다.

기존 로그인 없는 앱의 기록은 자동으로 서버에 올리거나 다른 계정에 섞지 않는다.

## 7일 보관

서버 시간과 최초 입력 시각을 기준으로 만료 항목을 조회·저장 결과에서 제외한다. 내용 수정으로 최초 입력일을 연장하지 않는다. 서버 정리 작업은 만료 기록을 주기적으로 제거한다. 무료 프로젝트가 일시 중지되면 정리 작업도 멈출 수 있으므로 재개 후 첫 조회에서 만료 기록을 정리한다. 받은 엑셀은 앱의 자동 삭제 대상이 아니다.

## 무료 조건 확인 (2026-10-02)

Supabase Free: 월 $0, 월 활성 사용자 50,000명, 데이터베이스 500MB, 전송량 5GB. 5명의 텍스트 시험은 이 범위에서 운영하도록 구성한다. 사용량이 초과되면 유료로 전환하지 않고 시험을 중단·조정한다. 1주 동안 낮은 사용량이면 프로젝트가 일시 중지될 수 있으며 무료 요금제에는 가용성 보장이 없다.

## 공개 전 확인

실제 인증 계정 2개 이상으로 교차 조회·수정·삭제 차단을 검사한다. 휴대폰 입력 → 서버 저장 완료 → PC 로그인 → 같은 기록 조회 → XLSX 다운로드를 확인한다. 잘못된 비밀번호·로그아웃·세션 만료·오프라인 입력·기기 간 동시 수정·7일 경계를 시험한다. 실제 비밀번호나 현장 데이터는 공개하지 않는다.

서버의 계정 분리·7일 보관·동시 수정 방지는 실제 PostgreSQL 엔진으로 검사한다. 시험용 도구는 공개하지 않는 `.test-output/cloud-tools`에 설치한다.

```powershell
npm install --prefix .test-output/cloud-tools --cache .test-output/npm-cache --no-audit --no-fund --save-exact @electric-sql/pglite@0.5.8
$env:NODE_PATH=(Join-Path (Get-Location) '.test-output/cloud-tools/node_modules')
node --test tests/account-db.test.cjs
```

실제 서버 프로젝트 생성과 관리자 로그인은 사용자가 직접 진행해야 한다. 서버 연결과 검증이 끝나기 전에는 5명에게 계정을 배포하지 않는다.

## 무료 서버 연결 순서

1. 사용자가 Supabase에 가입·로그인한다. 조직의 요금제는 **Free ($0)**로 선택하고 펀치리스트 전용 프로젝트 하나를 만든다. 프로젝트 이름은 `field-punch-list-pilot`을 기본안으로 제안한다. 다른 프로젝트는 열거나 변경하지 않는다. 데이터베이스 비밀번호는 사용자 비밀번호 관리자에 보관하며 저장소·채팅에 적지 않는다.
2. 인증 설정에서 신규 공개 회원가입을 끈다. 이메일·비밀번호 로그인을 사용한다. SMS, 유료 SMTP, 유료 부가 기능을 추가하지 않는다. 프로젝트의 Site URL은 기존 GitHub Pages 주소로 지정한다.
3. 전용 프로젝트의 SQL Editor에서 `server/account-schema.sql`을 실행한다. Cron 확장을 활성화하고 `server/retention.sql`을 실행한다. 만료 정리 작업의 실행 결과를 확인한다.
4. 인증 관리 화면에서 시험용 계정 5개를 생성한다. 로그인 아이디는 `pilot01` ~ `pilot05`를 기본안으로 제안한다. 인증 식별자는 `pilot01@accounts.field-punch-list.invalid` 형식이고 실제 연락 이메일이 아니다. 관리자 생성 시 이메일 확인 완료 상태로 만든다. 각 계정에는 서로 다른 임의 비밀번호를 발급하며 공개 코드·문서·시험 결과에 남기지 않는다. 이 별칭에는 이메일 비밀번호 재설정이 도착하지 않으므로 분실 시 관리자가 재발급한다.
5. 생성된 각 Auth 사용자 UUID와 아이디를 `punch_private.members`에 등록한다. 인증 계정만 만들고 이 허용 목록에 등록하지 않으면 앱을 사용할 수 없다. 실제 등록 SQL·UUID 목록·계정 전달 자료는 공개하지 않는다.
6. `cloud-config.js`에 전용 프로젝트의 HTTPS URL과 **publishable 키**(또는 legacy anon 키)만 넣는다. secret/service-role 키는 사용하지 않는다. 관리자 키를 공개한 뒤 삭제하는 방식으로 진행하지 않는다. 실제 서버로 두 계정 이상 로그인해 아래 검증을 마친 뒤 `enabled:true`로 공개할 준비를 한다.
7. 공개 점검 결과를 사용자에게 보여 주고 승인을 받은 뒤 이 저장소에만 push한다. Pages 반영과 휴대폰·PC 확인 후 계정을 각 시험 사용자에게 전달한다. 전달은 사용자가 직접 한다.

## 실제 서버 검증 체크

- 로그인 없는 요청, 잘못된 비밀번호, 미등록·비활성 계정은 기록을 읽거나 저장하지 못한다.
- A의 기록·현장 설정이 B에게 표시되지 않는다. B의 토큰으로 A의 번호를 넣거나 테이블을 직접 조회·변경해도 접근하지 못한다.
- 같은 계정의 휴대폰에서 ‘서버 저장 완료’ 후 PC에서 ‘최신 기록 불러오기’로 조회·XLSX 받기가 된다. PC의 현재 입력 세대는 휴대폰 설정을 바꾸지 않는다.
- 오프라인 미전송 기록은 재접속·재시도 후 저장된다. 미전송 상태의 로그아웃은 막히며, 정상 로그아웃 후 다른 아이디에서는 이전 기록이 보이지 않는다.
- 오래된 기기에서 새 기록을 덮어쓰지 못한다. 로그인이 만료·철회되면 전송과 편집을 멈추고 비공개 화면을 숨긴다.
- 최초 입력 후 정확히 7일 경계의 기록은 조회에서 제외되고 실제 저장 내용과 Cron 실행에서도 정리된다. 내용 수정으로 최초 입력일이 바뀌지 않는다.
- 서버 응답과 인증 토큰은 서비스 워커 캐시에 저장되지 않는다. 브라우저에는 계정별 기록 캐시와 해당 탭의 세션만 남으며 비밀번호는 저장하지 않는다. 브라우저 자체의 비밀번호 저장 제안은 사용자가 결정한다.

실제 서버 검증 전의 로컬 자동시험에는 응답을 재현한 시험 서버를 사용한다. 인증 서비스의 실제 설정·네트워크·권한 검증을 대신하지 않는다. 월 사용량은 관리 화면에서 확인하며 무료 범위를 넘으면 유료 전환 없이 시범 운영 범위를 줄인다.
